Why SpaceX

SpaceX is not a random pick. There are three reasons.

1. They have said they will pick the best tool

On 7 October Elon Musk said SpaceX will use the best back-end model for each task. He was talking about models, not search. I expect the same rule to reach search, and under that rule a search provider gets in by being more accurate on SpaceX's own work.

Going forward, @SpaceX will use the best back end model for any given task, including Claude Opus 5.5, MidJourney, Suno and other leading APIs. Whatever is most likely to give you the best outcome.

Elon Musk, 7 October 2026. link

2. Compliance is heavy there, and it is a search problem

SpaceX is the largest satellite operator. That means launch licenses, spectrum orders, launch insurance, and the law of every country it sells service in, much of it not in English. In Canada the decision is often in French, and the English summary is a different document. A compliance specialist I know at an Entrepreneur First company told me this is a real problem, and the company's CEO and CTO said the same. If Keenable does this well for SpaceX, the same work carries over to every space operator behind it, including newer ones like Starcloud.

3. It is a way into Cursor and Grok

Cursor joined SpaceX on 14 August 2026. Compliance is the first job; the larger prize is a place as a search provider inside Grok and Cursor. My rough estimate is that this alone would more than double Keenable's daily queries, and the queries are data Keenable can learn from. Developers rarely want to depend on one search provider. Exa is the visible incumbent: it publishes a Cursor plugin, though I don't know whether Cursor's own agent uses it. A Keenable listing next to Exa in Cursor puts the name in front of millions of developers.

None of this works unless Keenable is accurate on the compliance work. That is what the rest of this document tests.

How I'm comparing them

Inside Grok or Claude, search is one tool among many, so a bad answer is hard to blame on search. Here the search tool is the only thing that changes. Every column runs x-ai/grok-4.7 with the same instructions (find sources, read the pages, answer, cite the URLs, say what you could not verify) and the same budget of {% if study and study.budget %}{{ study.budget.max_tool_calls }} tool calls and {{ study.budget.max_seconds | int }} seconds{% else %}30 tool calls and 600 seconds{% endif %}. A run that hits the budget is made to answer, and that answer is graded like any other.

Two exceptions. SELECT gets a short note on how to write its SQL, because that is how SELECT is meant to be used. The router, Jev (typesafe/jev-1.13), picks search or SELECT once per question, and then the agent has only that tool.
